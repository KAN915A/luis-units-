## Command-word ladder (from the BTEC glossary + spec descriptors)

| Level | Word     | What it means in a Unit 22 answer                                                                                 |
| ----- | -------- | ----------------------------------------------------------------------------------------------------------------- |
| Pass  | **Explain** | Give reasons why or how, using the correct terminology. Not just a definition — say **what it is**, **how it works**, and **why it is used**. |
| Merit | **Assess** | Weigh up strengths and weaknesses to reach a judgement about **suitability** for a purpose — here, for modelling business processes. |
| Distinction | **Evaluate** | Go further than assessment: give a **justified conclusion** with alternatives considered, supported by scenario evidence. |

## What Task 1 requires — grade-band checklist

### For 22/A.P1 — Explain the principles of software development models

Explain **more than one** software development model. Cover the *principles*, not just the name. Suggested models:

- [ ] **Waterfall SDLC** — sequential phases, sign-offs, stability. (Unit 3 D1, Topic 14, Topic 15.)
- [ ] **Prototyping** — iterative, users see a scaled-down working version early. (Topic 17.)
- [ ] **Rapid Application Development (RAD)** — prototyping-centred, time-boxed, JAD. (Topic 17 + Topic 18, Fig 1.16.)
- [ ] *(Optional but strong)* **Iterative / Agile** for contrast — sprint-based, incremental delivery.

For each model, explain:
- The **principle** (the core idea).
- The **phases / process**.
- **Advantages + disadvantages**.
- **When you'd use it** (in one sentence).

### For 22/A.P2 — Explain the features of systems analysis tools & techniques

Explain the **features** of several tools/techniques used to **model business processes**. Suggested (matches Week 1 + the brief's own sources):

- [ ] **Data Flow Diagram (DFD)** — external entities, processes, data stores, data flows; level 0 / level 1 decomposition. (Topics 5, 7.)
- [ ] **Entity Relationship Diagram (ERD)** — entities, attributes, relationships, cardinality. (Topics 4, 8.)
- [ ] **Data dictionary** — one row per field: name, type, size, source, use. (Topic 4.)
- [ ] **Decision table / decision tree** — expressing processing logic. (Topic 5.)
- [ ] **Structured English / pseudocode** — expressing processing logic. (Topic 5.)
- [ ] **Flowchart** — visual process description. (Topic 5.)
- [ ] **State diagram** — object lifecycles. (Topic 5.)
- [ ] **CASE tools** — Computer-Aided Software Engineering tools that automate diagramming, code generation, and traceability. (Cite from the brief's sources.)
- [ ] **Prototyping method (Fig 1.16)** as an analysis tool. (Topic 18.)

For each tool/technique, explain:
- **What it shows** (its features / notation).
- **What analysis question it answers**.
- **When you would use it**.

### For 22/A.M1 — Assess the suitability of tools & techniques for modelling business processes

Move beyond features into **judgement**: how well does each tool actually **model business processes**? For each tool covered under P2:

- [ ] Strengths — what it captures well.
- [ ] Weaknesses / limits — what it misses or distorts.
- [ ] Suitability — which kinds of business process it fits, and which it does not.
- [ ] Comparison — e.g. DFD vs Flowchart for the same process; ERD vs Data Dictionary for the same data.

### For 22/A.D1 — Evaluate the suitability of tools & techniques for modelling business processes

Move beyond Assess: reach a **justified conclusion** with **alternatives considered** and **scenario evidence**:

- [ ] Apply the tools directly to the **Say-It-With-Cards e-card business processes**.
- [ ] Recommend which tool best fits each type of process (customer sign-up, sending an e-card, managing the diary, payment).
- [ ] Compare recommendations against alternatives; justify why one wins.
- [ ] Conclude with a **justified overall recommendation** for the e-card project.
- [ ] Consider trade-offs (cost, learning curve, tool interoperability, CASE tool support).

## Suggested report skeleton (aligned to the criteria)

1. **Introduction**
   - Purpose (per the brief).
   - Audience (Say-It-With-Cards client).
   - Overview of the e-card system business needs (10 customer bullets from the scenario).

2. **Part A — Software development models** *(covers 22/A.P1)*
   - Model 1: Waterfall SDLC — principle, phases, advantages, disadvantages, when to use.
   - Model 2: Prototyping — principle, throwaway vs evolutionary, advantages, disadvantages.
   - Model 3: RAD — Fig 1.16 method, JAD, time-boxing.
   - *(Optional)* Model 4: Iterative / Agile for contrast.
   - Short comparison table.

3. **Part B — Systems analysis tools & techniques** *(covers 22/A.P2 explain, 22/A.M1 assess, 22/A.D1 evaluate)*
   - For **each** tool/technique below, structure the sub-section as:
     - **Features** (P2)
     - **Suitability assessment for business-process modelling** (M1)
     - **Evaluation + justified recommendation for the e-card scenario** (D1)
   - Tools to cover: DFD, ERD, data dictionary, decision table, structured English, flowchart, state diagram, CASE tools, prototyping-as-analysis-tool.

4. **Part C — Applied to the e-card system** *(supports D1)*
   - The Say-It-With-Cards e-card business processes named:
     - Customer sign-up + secure login.
     - Card personalisation.
     - Diary + reminders.
     - Address book management.
     - Sending an e-card.
     - Payment.
     - Social-media linking + upload.
   - For each business process, recommend the most suitable tool(s) from Part B and justify.

5. **Conclusion + justified recommendation** *(D1)*
   - The overall best-fit tool set for the e-card project.
   - The overall best-fit software development model for the project (likely hybrid: RAD-style for the customer UX, Waterfall discipline for payment + login, per Topic 17).
   - Next steps for the project team.

6. **References** — every source cited with a link, in alphabetical order.

7. **Appendices** — sample diagrams (DFD level 0, ERD extract, data-dictionary extract, decision-table example), all sized against the e-card scenario.
